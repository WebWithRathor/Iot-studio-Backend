# Kokoon LMS ↔ IoT Studio integration

The Kokoon LMS (block editor) and IoT Studio are connected in three ways:

```
 Student browser            Kokoon LMS backend                 IoT Studio API                 Board
 ───────────────            ──────────────────                 ──────────────                 ─────
 "Open IoT Studio"  ──────▶ mint SSO JWT (LMS_SSO_SECRET)
 auto-posting form  ───────────────────────────────────────▶ POST /auth/lms/sso
                    ◀────────────────── 303 + session cookies ─┘  (A)

 "Flash"            ──────▶ PUT /integrations/lms/devices/{hw}
                            signed HMAC (LMS_API_SECRET) ────▶ upsert device, project,
                            ◀─── broker + credentials (B1) ──  variables (firmwareRef)
                            build firmware with credentials ─────────────────────────────▶ flash
                                                                MQTT broker ◀──────────── telemetry / ack
                                                                dashboards  ─────────────▶ commands  (C)
```

The binding contract (v1) is below, unchanged, followed by the backwards-compatible
v1.1 additions (chip binding, bulk status, rate limits, reserved ids). Together they are
the only thing the LMS team implements against; the "Implementation notes" after them
describe how IoT Studio implements them and where it adds behaviour they leave open.

## Contract

```text
=== INTEGRATION CONTRACT v1 ===================================================

Systems
- LMS: block editor (prod/test: https://test.kokoon.pre.pixxo.io/). Generates and flashes
  firmware for ESP32 / Kokoon BrainBoard.
- IoT Studio API base {IOT_API} (dev http://localhost:4004/api/v1), app {IOT_APP}
  (dev http://localhost:5180, hash routes such as /#/devices/<id>).
- MQTT broker for devices: {MQTT_PUBLIC_BROKER_URL} (dev mqtt://<LAN-IP>:1883,
  prod mqtts://<host>:8883). Topic root: kokoon/devices.

Secrets (server-side only; never in a browser bundle, never in logs)
- LMS_SSO_SECRET  — HS256 key for SSO tokens, ≥48 chars.
- LMS_API_SECRET  — HMAC-SHA256 key for server-to-server calls, ≥48 chars, different.

A. SSO (LMS user → IoT Studio session)
1. The LMS backend mints a JWT, HS256, signed with LMS_SSO_SECRET:
   { "iss":"kokoon-lms", "aud":"kokoon-iot-studio", "sub":"<lmsUserId>",
     "email":"<email>", "email_verified":true|false, "name":"<display name>",
     "jti":"<uuid v4>", "iat":<unix s>, "exp":<iat+60> }
2. The LMS sends the browser a page that auto-submits a top-level form POST
   (application/x-www-form-urlencoded) to {IOT_API}/auth/lms/sso with fields
   token=<jwt> and optional next=<hash route, e.g. /devices/abc or /projects/xyz>.
3. IoT Studio verifies signature, iss, aud, exp (≤30 s clock skew), and that jti
   was never used (Redis, TTL 120 s). It finds the user by lmsUserId. If none exists:
   link an existing local user with the same email ONLY if email_verified is true and that
   user has no lmsUserId yet; otherwise create a user (role USER, plan FREE, authProvider
   "lms"). The token never grants or changes a role or plan.
4. On success: issue the normal access + refresh cookies and 303-redirect to
   {FRONTEND_URL}/#<next>. next must start with "/", contain no "//", and match a known
   app route; otherwise use "/".
5. On failure: 303 to {FRONTEND_URL}/#/login?sso_error=<expired|invalid|replayed|disabled|unavailable>.
6. Reverse direction: IoT Studio's login page has a "Sign in with Kokoon LMS" button that
   navigates to {LMS_URL}/iot-studio/sso-start?next=<route>. The LMS signs the student in if
   needed, then does steps 1–2.

B. Server-to-server API (LMS backend → IoT Studio), base {IOT_API}/integrations/lms
Every request carries:
  X-Kokoon-Timestamp: <unix seconds>
  X-Kokoon-Request-Id: <uuid v4>              (idempotency key, remembered 24 h)
  X-Kokoon-Signature: sha256=<hex HMAC-SHA256(LMS_API_SECRET,
                       timestamp + "." + METHOD + "." + pathWithQuery + "." + rawBody)>
  Content-Type: application/json
Reject: |now − timestamp| > 300 s, a bad signature (constant-time compare), or a reused
Request-Id with a different body. A reused Request-Id with the same body returns the
original response. No cookies, no X-Requested-With.
Errors: { "error": { "code": "<snake_case>", "message": "<text>" } } with codes
invalid_signature (401), stale_timestamp (401), validation_failed (422),
device_owned_by_other_user (409), user_disabled (403), not_found (404),
integration_disabled (503).

B1. PUT /integrations/lms/devices/{hardwareId}[?rotateCredentials=true]
    Upsert the board a student flashed. hardwareId matches ^[a-z0-9][a-z0-9-]{2,47}$,
    is generated by the LMS once per physical board and is globally unique.
    Request:
    {
      "user":    { "lmsUserId":"u_123", "email":"asha@example.com", "emailVerified":true, "name":"Asha" },
      "device":  { "name":"Desk ESP32", "board":"ESP32-S3 DevKitC", "firmwareVersion":"r14" },
      "program": { "programId":"prog_abc", "name":"Room Monitor", "version":"r14" },
      "variables": [
        { "key":"temperature", "displayName":"Temperature", "dataType":"float",
          "direction":"telemetry", "unit":"°C", "min":0, "max":50, "blockId":"blk_9f" },
        { "key":"led_state", "displayName":"LED", "dataType":"boolean",
          "direction":"bidirectional", "blockId":"blk_a1" }
      ],
      "project": { "create": true }
    }
    board ∈ "ESP32-S3 DevKitC" | "ESP32-C3 Mini" | "Kokoon BrainBoard" | "ESP32 WROOM-32".
    key ^[a-z][a-z0-9_]{0,39}$, unique per device, max 30 variables.
    dataType ∈ boolean | integer | float | string | color | json.
    direction ∈ telemetry | command | bidirectional.
    Response 201 (created) / 200 (updated):
    {
      "deviceId":"...", "hardwareId":"...", "topicPrefix":"kokoon/devices/<hardwareId>",
      "broker": { "url":"mqtt://192.168.1.20:1883", "host":"192.168.1.20", "port":1883, "tls":false },
      "credentials": { "username":"...", "password":"..." } | null,
      "projectId":"..." | null,
      "studioUrl":"{IOT_APP}/#/devices/<deviceId>",
      "warnings": [ "insufficient_tokens_project_not_created" ]
    }
    credentials is non-null only when the device is first created or rotateCredentials=true.
    The password is shown once and never stored in plain text by IoT Studio.
    Semantics: the user is resolved/created exactly like SSO step 3. The device is
    origin "lms", simulated false, lmsProgram {..., source:"lms"}. "variables" REPLACES the
    device's declared capabilities. If project.create is true, reuse this user's project
    whose lmsProgram.programId matches (else create one named after the program), associate
    the device, and upsert one project variable per declared key with
    firmwareRef {source:"lms", blockId, variableName:key} and conventional topics.
    Variables no longer declared are kept but flagged "no longer declared by firmware".
    Normal token costs apply. If the user can't afford them, the device is still saved,
    projectId is null and a warning is returned.
B2. GET    /integrations/lms/devices/{hardwareId} → { deviceId, hardwareId, ownerLmsUserId,
           connectionState, lastSeenAt, projectIds, studioUrl }
B3. DELETE /integrations/lms/devices/{hardwareId} → disables the device and revokes its
           broker credentials (204).

C. Firmware MQTT contract (what LMS-generated code does)
- Connect with clientId = hardwareId and username/password = the device credentials.
  Keepalive 30 s, clean session.
- Last Will: topic {prefix}/availability, payload {"state":"offline"}, retain true, QoS 1.
- On connect: publish {prefix}/availability {"state":"online"} retained, then subscribe
  {prefix}/command/+ (QoS 1).
- Telemetry: publish {prefix}/telemetry/{key}, payload {"value":<v>} (optional "unit"),
  QoS 0, not retained, at most 1 message per second per key.
- Commands: the device receives {prefix}/command/{key} with payload {"value":<v>} (may include
  "unit"). It applies the value, then within 5 s publishes {prefix}/ack/{key} with
  {"value":<applied>,"ok":true} or {"ok":false,"error":"<≤120 chars>"}. For bidirectional
  keys it also publishes the new state on {prefix}/telemetry/{key}.
- Values: boolean → true/false; integer → JSON integer; float → JSON number;
  string → ≤256 chars; color → "#rrggbb" lowercase; json → object, depth ≤4.
- Limits: payload ≤4096 bytes, no control characters, topic ≤200 chars, ≤10 levels,
  characters [A-Za-z0-9_-./].
- Reconnect Wi-Fi and MQTT with backoff 1 s → 30 s, without blocking the user's loop.

D. Mapping
- LMS program → lmsProgram {programId, name, version, source:"lms"} on the device and project.
- "declare IoT variable" block → device capability + project variable with firmwareRef.blockId.

=== END CONTRACT ==============================================================
```

## Contract v1.1 additions

All optional for the LMS; a v1 client keeps working unchanged.

```text
B1. PUT /integrations/lms/devices/{hardwareId}[?rotateCredentials=true][&replaceChip=true]
    "device" may carry "chipId": the board's machine.unique_id() as lowercase hex,
    ^[0-9a-f]{8,32}$. IoT Studio binds the hardware id to that chip.
    - chipId omitted: exactly the v1 behaviour (an existing binding is kept).
    - Same chipId as bound (or first chipId): normal upsert.
    - Different chipId than bound, no replaceChip:
        409 {"error":{"code":"chip_mismatch","message":"…"}}
      The LMS offers "Replace" and retries with &replaceChip=true.
    - replaceChip=true: binds the new chipId AND rotates the broker credentials
      (response carries the new credentials; the old chip is disconnected and
      locked out).
    - A chipId is bound to at most ONE active device. Another active device on it:
        409 {"error":{"code":"chip_in_use","message":"…","details":{"hardwareId":"<other>"}}}
      "details" is present only when that other device belongs to the same user.
      A device disabled with B3 frees its chip.
B1. hardwareId must not equal the broker accounts MQTT_USERNAME / MQTT_DEVICE_USERNAME
    and must not start with "kokoon-backend", "admin", "sandbox-", "esp32-sim-"
    (422 validation_failed). LMS-generated ids look like kk-<board>-<random>.
B1. If the broker account cannot be created or updated: 503 unavailable. Retry the
    same request (same X-Kokoon-Request-Id is fine); the retry returns the credentials.
    Never treat a 503 as "credentials:null".
B2. The single-device response also carries "chipId" (string or null).
B4. POST /integrations/lms/devices/status   (signed like every call: method POST, raw JSON body)
    Request:  {"hardwareIds":["kk-…", …]}   1..200 ids, each ^[a-z0-9][a-z0-9-]{2,47}$
    Response 200:
    { "devices": [ { "hardwareId","deviceId","ownerLmsUserId","connectionState",
                     "lastSeenAt","studioUrl" } ],
      "missing": [ "<ids that are unknown or not LMS devices>" ] }
    Read-only and not idempotency-stored (X-Kokoon-Request-Id is still required and
    checked for format). Use it instead of one B2 per open panel.
Rate limits. Signed calls are limited per caller after the signature check:
    LMS_API_RATE_LIMIT_PER_MIN (default 6000/min) shared by all LMS backend instances.
    Requests failing the signature check: 600/min per IP. 429 rate_limited carries
    Retry-After = seconds until the window resets; honour it.
```

### Clarifications the LMS side needs

- **`pathWithQuery` includes the API base path.** Sign exactly what goes on the
  HTTP request line, e.g.
  `/api/v1/integrations/lms/devices/kk-esp32s3-7f3k9q2m?rotateCredentials=true`.
- The body is signed as raw bytes; send exactly the bytes you signed.
  For GET and DELETE the body is empty (`timestamp.GET.path.`).
- Hex in `X-Kokoon-Signature` may be upper or lower case.
- Error responses also carry `"requestId"` (IoT Studio's log correlation id) next to `"error"`;
  422 errors may include `"details": { "fieldErrors": {…}, "formErrors": […] }`.
- Successful B1/B2 bodies are plain JSON (no `{ success, data }` envelope).
- `email_verified` missing from the SSO token counts as `false`.
- An SSO token may live at most 120 s (`exp − iat`); `iat` may be at most 30 s in the future.
- Reserved hardware ids answer 422 `validation_failed` on B1, B2 and B3: the prefixes
  `kokoon-backend`, `admin`, `sandbox-`, `esp32-sim-`, and any id equal to (or starting
  with `<name>-` for) `MQTT_USERNAME`, `MQTT_DEVICE_USERNAME` or `MQTT_CLIENT_ID`
  (the backend's broker client id is `<MQTT_CLIENT_ID>-<pid>`). B4 just lists them as missing.

### Additions to the contract (retryable, never returned for a client mistake)

| Status | Code | When | What the LMS should do |
| --- | --- | --- | --- |
| 503 | `request_in_progress` | the same Request-Id is still being processed | retry after `Retry-After` |
| 429 | `rate_limited` | more than `LMS_API_RATE_LIMIT_PER_MIN` signed requests/min (or 600/min unsigned from one IP) | retry after `Retry-After` (seconds until the window resets) |
| 503 | `request_in_progress` | a parallel request for the same board, same student, is creating it | retry after `Retry-After` |
| 503 | `unavailable` | database, Redis or broker down; B1 could not issue the broker account; B3 could not revoke it | retry with backoff, same Request-Id |
| 500 | `internal_error` | a bug | retry later; report the `requestId` |
| 413 | `validation_failed` | body larger than the API's JSON limit | don't retry |

Other choices the contract leaves open:

- **Idempotency.** Only writes (PUT, DELETE) are remembered. A request that fails
  (any error response) releases its Request-Id, so the LMS can retry with the same id.
  An unfinished reservation expires after 120 s (e.g. if the server crashed mid-request);
  a finished response is remembered for 24 h.
  Replayed responses carry `X-Kokoon-Idempotent-Replay: true`. Stored responses are
  encrypted at rest in Redis (they can contain device credentials).
- **jti memory** is 180 s (token max lifetime + 2 × skew), longer than the contract's 120 s,
  so a token can never outlive its replay record.
- **Credentials** are also issued when a device disabled with B3 is flashed again (it is
  re-enabled), on `replaceChip=true`, and on any retry after an earlier attempt failed to
  issue them: the device stores `credentialsIssuedAt`, set to null whenever credentials are
  owed and filled only after the broker confirmed. So a B1 that answered 503 never leaves a
  board whose retry returns `credentials: null`. Issuing is idempotent on the broker
  (an existing account gets a new password; the old one stops working immediately).
- **Device cap.** `MAX_DEVICES_PER_USER` (50) counts only active devices for B1, so boards
  removed with B3 free their slot.
- **Retained availability.** B3 (and a chip replace) publish an empty retained message on
  `{prefix}/availability`: the broker disconnects the old board without its Last Will, so its
  retained `"online"` would otherwise stay.
- **Bulk status** reads the devices with one `$in` query and their owners with one more;
  `connectionState` / `lastSeenAt` come from the live registry like B2.
- **B2/B3 only see LMS devices.** A device created in IoT Studio itself answers 404.
- **B2 `connectionState`** is one of `connected | connecting | disconnected | waiting | auth_required | error`,
  or `disabled` after B3.
  `lastSeenAt` is unix **milliseconds** or `null`.
- **User linking by email** happens only when the email is verified and the local
  account has no LMS id. If the email is unverified and already taken, SSO fails with
  `sso_error=invalid` and B1 with 422 `validation_failed` (`details.fieldErrors["user.email"]`).
  A disabled IoT Studio account gives `sso_error=disabled` / 403 `user_disabled`.
- **Project creation** reuses the student's project whose `lmsProgram.programId` matches.
  New projects use category Custom, icon `LuGraduationCap`, accent indigo. Besides
  `insufficient_tokens_project_not_created`, B1 may return the warnings
  `project_limit_reached_project_not_created` and `variable_limit_reached`
  (the project already has the maximum number of variables).
- **Variable keys.** If a project already has a variable with the declared key that is
  not linked to this device's firmware, the new one is created as `key_2` (`key_3`, …).
  A declaration is matched to an existing variable of this board by key, then by `blockId`
  (the student renamed the key in the same block: the variable is renamed and keeps its
  widgets), then to a variable made by hand in IoT Studio with that key. Direction, type,
  name, unit and range always follow the latest declaration.
- **Removed declarations.** LMS variables of this board that the program no longer declares
  are **deleted** (widgets bound to them are unbound), replacing the contract's "kept but
  flagged". The activity log records which keys were removed.
- **Live refresh.** After every B1 the owner's open IoT Studio tabs get an `lms_sync` stream
  event (`{deviceId, projectId, removedVariableIds}`) and re-read devices, projects and
  variables, so a dashboard shows new directions or removed keys without a reload.
  Students can also delete any variable from a widget's Data tab.
- **LMS users and passwords.** LMS-created accounts have `passwordSet: false`; password login
  is refused (generic "invalid credentials") until the student sets a password under
  Profile, which does not ask for a current password in that case.
- **SSO and CORS.** `POST /auth/lms/sso` is mounted before CORS and the CSRF header rule
  (it is a top-level form navigation). If an `Origin` header is present it must be the
  LMS origin; `Origin: null` (a local file from `npm run lms:sso`) is accepted only when
  `NODE_ENV=development`. Rate limit: 60 per 15 min per IP.
- **Acks.** `{"ok":false,"error":"…"}` marks the command `failed` with reason
  `Device: <error>` (control characters stripped, ≤120 chars). Anything else, including
  non-JSON payloads, still counts as acknowledged.

### Broker credentials

| `BROKER_CREDENTIALS_MODE` | What a device gets | Use |
| --- | --- | --- |
| `shared` (default) | `MQTT_DEVICE_USERNAME` / `MQTT_DEVICE_PASSWORD` for every board | development only; refused in production |
| `mosquitto-dynsec` | its own client (`username = clientId = hardwareId`, random password) and role `device-<hardwareId>`: publish `<prefix>/telemetry/#`, `<prefix>/ack/#`, `<prefix>/availability`; subscribe / unsubscribe `<prefix>/command/#` | required in production; needs `MQTT_MODE=broker` |

In dynsec mode the backend, on start-up, creates the role `kokoon-backend`
(publish and subscribe on `kokoon/#`) and assigns it to `MQTT_USERNAME` (safe to repeat
on every start). B3 deletes the device's client and role. Rotation sets a new password
(the broker disconnects a board using the old one) and re-enables the client.

How the backend talks to the plugin (checked against the Mosquitto 2.0.22 sources):

- One `$CONTROL/dynamic-security/v1` message per step, with a `commands` array; every
  command carries its own `correlationData`, matched against
  `$CONTROL/dynamic-security/v1/response` (`{"responses":[{command, error?, data?, correlationData}]}`),
  so concurrent requests and other backend instances never mix answers. No answer within
  5 s → a retryable error (B1/B3 answer 503).
- Mosquitto 2.0 rewrites `dynamic-security.json` after every successful mutating command,
  so a new board is created with exactly two: `createRole` (with its ACLs) and `createClient`
  (with the role), in one message. Re-issuing an existing account reads it with `getClient`
  and then sends only what is needed (`setClientPassword`, plus `modifyRole` /
  `enableClient` / `addClientRole` when required; `addClientRole` for a role the client
  already has would fail with "Internal error").
- The service refuses to touch any reserved account name, and refuses an existing account
  whose client id is not the hardware id or that has roles other than `device-<hardwareId>`.

Dev broker with dynamic security:

```bash
npm run deps:up:broker-dynsec
# .env: MQTT_MODE=broker, BROKER_CREDENTIALS_MODE=mosquitto-dynsec,
#       MQTT_USERNAME=kokoon-backend, MQTT_PASSWORD=kokoon-dev-mqtt
```

`MQTT_BIND_ADDRESS` (default `127.0.0.1`) controls which interface the dev broker
listens on. Set it to `0.0.0.0` so a board on your Wi-Fi can reach
`MQTT_PUBLIC_BROKER_URL=mqtt://<your-LAN-IP>:1883`. Only do that on a trusted network.

Broker sizing (both compose profiles, `eclipse-mosquitto:2.0.22`): `ulimits nofile 65536`
(Docker on Linux otherwise caps a container at ~1024 sockets), `max_connections -1`,
`max_packet_size 8192`, `max_inflight_messages 20`, `max_queued_messages 1000`,
`set_tcp_nodelay true`, persistence with `autosave_interval 300`, a `$SYS` healthcheck
and log rotation. `max_keepalive` is left unset on purpose (it would refuse MQTT 3.1.1
clients with keepalive 0). For production uncomment the 8883 TLS listener in
`docker/mosquitto/mosquitto-dynsec.conf` and its port/cert mount in `docker-compose.yml`.

Production behind a reverse proxy or load balancer: set `TRUST_PROXY` to the number of
proxies (usually 1). With the default 0 every request seems to come from the proxy's IP,
so all per-IP limits (unsigned LMS calls, SSO, the general API) are shared by everyone.

### Try it without the LMS

```bash
# .env: LMS_INTEGRATION_ENABLED=true, LMS_URL, both secrets (npm run setup:env generates them),
#       MQTT_PUBLIC_BROKER_URL, MQTT_DEVICE_USERNAME / MQTT_DEVICE_PASSWORD; restart the API.
npm run lms:sso -- --sub u_test --email tester@kokoon.local --name "Test Student" --next /devices
npm run lms:device -- --hardware kk-esp32s3-test01 --sub u_test --email tester@kokoon.local
npm run lms:device -- --hardware kk-esp32s3-test01 --get
npm run lms:device -- --hardware kk-esp32s3-test01 --delete
```

The same signed call with curl (bash):

```bash
TS=$(date +%s); RID=$(uuidgen | tr A-Z a-z)
PATHQ=/api/v1/integrations/lms/devices/kk-esp32s3-test01
BODY='{"user":{"lmsUserId":"u_test","email":"tester@kokoon.local","emailVerified":true,"name":"Tester"},"device":{"name":"Desk ESP32","board":"ESP32-S3 DevKitC"},"program":{"programId":"prog_demo","name":"Room Monitor"},"variables":[{"key":"temperature","displayName":"Temperature","dataType":"float","direction":"telemetry","blockId":"blk_1"}],"project":{"create":true}}'
SIG=$(printf '%s' "$TS.PUT.$PATHQ.$BODY" | openssl dgst -sha256 -hmac "$LMS_API_SECRET" -hex | sed 's/^.* //')
curl -sS -X PUT "http://localhost:4004$PATHQ" -H "Content-Type: application/json" \
  -H "X-Kokoon-Timestamp: $TS" -H "X-Kokoon-Request-Id: $RID" -H "X-Kokoon-Signature: sha256=$SIG" \
  --data-binary "$BODY"
```

### Audit log actions

`lms.sso.login`, `lms.sso.rejected` (reason; the token is never logged), `lms.user.linked`,
`lms.user.created`, `lms.api.rejected`, `lms.device.upserted`, `lms.device.credentials`
(reason created / reenabled / chip_replaced / rotated / retried, never the password), `lms.device.disabled`.

### Not done / limitations

- Mongo transactions are not used for B1; it is made safe by the unique hardwareId index,
  the idempotency reservation, and the wallet lock in project creation. A crash between
  "device saved" and "project created" leaves a device without a project; the LMS's
  retry with the same Request-Id completes it.
- The dynsec provider and the Mosquitto configs were checked against the 2.0.22 plugin
  sources and unit-tested with a fake transport, but not run against a real broker.
- Admin device operations (disable, delete, owner or prefix change in IoT Studio itself)
  do not update the broker account; only B1/B3 do.
- With `shared` credentials every board can publish on every device's topics.
