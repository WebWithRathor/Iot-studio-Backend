# Kokoon Backend — Kokoon IoT Studio API

Express + TypeScript API for **Kokoon IoT Studio**: accounts and sessions, projects,
dashboards, widgets, variables, devices, and the MQTT pipeline (telemetry in,
commands out, live updates to the browser over Server-Sent Events).

| | |
|---|---|
| Runtime | Node.js ≥ 20.11, TypeScript (CommonJS build) |
| HTTP | Express 4, Helmet, CORS (allow-list), cookie-parser |
| Data | MongoDB 7 via Mongoose 8 (DAO layer, transactions when a replica set is available) |
| Sessions / cache / rate limits | Redis 7 via ioredis |
| Auth | JWT access + refresh tokens in **HttpOnly cookies**, Argon2id password hashing |
| Validation | Zod — environment at startup, every request body / query / param |
| MQTT | MQTT.js (`MQTT_MODE=broker`) or the in-process loopback transport (`MQTT_MODE=simulated`) |
| Logging | Winston, JSON in production, secrets redacted, every DB operation traced |

> **Status:** development build. It runs locally and has a production-hardening
> path (see *Production checklist*), but it has not been load-tested,
> penetration-tested or deployed. Do not treat it as production-ready yet.

## 1. Quick start

Requirements: Node.js 20.11+, Docker Desktop (for MongoDB and Redis), and Git Bash or PowerShell.

### macOS / Linux / Git Bash

```bash
cd "Kokoon Backend"
npm install
npm run setup:env        # only if .env is missing — creates it with random dev secrets
npm run deps:up          # MongoDB (replica set rs0) + Redis on 127.0.0.1
npm run seed:dev         # dev student + admin accounts and a sample workspace (idempotent)
npm run dev              # http://localhost:4004/api/v1
```

### Windows PowerShell

```powershell
Set-Location "Kokoon Backend"
npm install
npm run setup:env
npm run deps:up
npm run seed:dev
npm run dev
```

Check it is up: open <http://localhost:4004/api/v1/health> (liveness) and
<http://localhost:4004/api/v1/health/ready> (MongoDB + Redis + MQTT readiness).

Then start **Kokoon Frontend** (`npm run dev` there) and open <http://localhost:5180>.
Use `localhost` for both — mixing `localhost` and `127.0.0.1` makes them different
sites and the browser will not send the session cookies.

### Development accounts

`npm run seed:dev` creates (or updates) two accounts from `.env`:

| Account | Email | Password |
|---|---|---|
| Student (`USER`) | `DEV_USER_EMAIL` (default `student@kokoon.local`) | `DEV_USER_PASSWORD` in `.env` |
| Admin (`ADMIN`) | `ADMIN_EMAIL` (default `admin@kokoon.local`) | `ADMIN_PASSWORD` in `.env` |

The passwords are random, generated by `npm run setup:env`. To create (or
promote) an administrator at any time — idempotent:

```bash
npm run create-admin                                     # uses ADMIN_EMAIL / ADMIN_PASSWORD / ADMIN_NAME from .env
npm run create-admin -- --email you@example.com --password "a-long-passphrase-1" --name "Your Name" --role SUPER_ADMIN
```

In production the script refuses to run without `--allow-production` and an
explicit password; there are no default production credentials.

### Real MQTT broker (optional)

```bash
npm run deps:up:broker                 # adds Mosquitto on 127.0.0.1:1883 (auth + ACL enabled)
# in .env:  MQTT_MODE=broker
npm run dev
```

Dev broker accounts (in `docker-compose.yml`): `kokoon-backend / kokoon-dev-mqtt`
for the API, `esp32-device / kokoon-dev-device` for a test board. Development only.

The broker listens on `127.0.0.1` only. To let a board on your Wi-Fi reach it, set
`MQTT_BIND_ADDRESS=0.0.0.0` (in your shell or `.env` next to `docker-compose.yml`) on a
trusted network. `npm run deps:up:broker-dynsec` starts a broker with Mosquitto's
dynamic-security plugin instead (one account per device, see the LMS integration).

### Kokoon LMS integration (optional)

Students can open IoT Studio from the Kokoon LMS already signed in, and a board flashed
from the LMS appears as a real device with the variables its blocks declared.
Contract and details: [docs/LMS-INTEGRATION.md](docs/LMS-INTEGRATION.md).

```
LMS ──form POST (signed JWT)──▶ /auth/lms/sso ──303 + cookies──▶ IoT Studio
LMS ──PUT /integrations/lms/devices/{hw} (HMAC)──▶ device + project + variables
    ◀── broker address + device credentials ── (LMS builds them into the firmware)
board ──MQTT telemetry / ack──▶ broker ◀── commands ── dashboards
```

1. In `.env`: `LMS_INTEGRATION_ENABLED=true`, `LMS_URL`, `LMS_SSO_SECRET`, `LMS_API_SECRET`
   (`npm run setup:env` generates both secrets; share them with the LMS backend only),
   `MQTT_PUBLIC_BROKER_URL` (the address boards use, e.g. `mqtt://<LAN-IP>:1883`) and, in
   the default `BROKER_CREDENTIALS_MODE=shared`, `MQTT_DEVICE_USERNAME` / `MQTT_DEVICE_PASSWORD`.
2. Restart the API. The login page now shows **Sign in with Kokoon LMS**.
3. Without the LMS: `npm run lms:sso -- --email you@kokoon.local` writes a local page that signs
   you in; `npm run lms:device -- --hardware kk-esp32s3-test01` registers a test board.

**Request flow:** route → middleware (auth, permission, validation) → controller →
service (business rules, ownership) → DAO (logged DB call) → model. ESLint rules
enforce the direction: controllers may not import DAOs or models, services may
not import Express, only DAOs import models.

## 4. API

Base URL `http://localhost:4004/api/v1`. Every response uses one envelope:

```json
{ "success": true,  "data": { },                                   "requestId": "…" }
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "…", "details": { } }, "requestId": "…" }
```

| Area | Endpoints |
|---|---|

| Users | `GET /admin/users`, `GET /admin/users/:id`, `GET /admin/users/:id/sessions`, `PATCH /admin/users/:id/role`, `PATCH /admin/users/:id/status`, `PATCH /admin/users/:id/plan`, `POST /admin/users/:id/sessions/revoke` |

### Kokoon LMS (`/integrations/lms/*`, server-to-server)

No cookies: every request is HMAC-signed with `LMS_API_SECRET` and writes are idempotent per
`X-Kokoon-Request-Id`. Responses use the contract's plain JSON and snake_case error codes,
not the envelope above. Verified calls are rate limited per caller
(`LMS_API_RATE_LIMIT_PER_MIN`, default 6000/min), bad signatures per IP (600/min).
See [docs/LMS-INTEGRATION.md](docs/LMS-INTEGRATION.md).

| Method | Path | |
|---|---|---|
| `PUT` | `/integrations/lms/devices/:hardwareId[?rotateCredentials=true][&replaceChip=true]` | Upsert a board flashed from the LMS, its variables and (optionally) its project; optional `device.chipId` binds it to one ESP32 (409 `chip_mismatch` / `chip_in_use`) |
| `GET` | `/integrations/lms/devices/:hardwareId` | Owner, connection state, bound chip, projects |
| `POST` | `/integrations/lms/devices/status` | Connection state of up to 200 boards at once (read-only) |
| `DELETE` | `/integrations/lms/devices/:hardwareId` | Disable it and revoke its broker access |

## 5. Authentication and sessions

- **Cookies only.** `access_token` (10 min, path = API base) and `refresh_token`
  (7 days, path = `/api/v1/auth`), both `HttpOnly`, `SameSite=Lax` by default,
  `Secure` required in production. Tokens are never returned in a response body
  and the frontend never stores them.
- **Refresh rotation with reuse detection.** Each refresh issues a new refresh
  token and atomically retires the old one (Redis Lua compare-and-swap). A short
  grace window covers two tabs refreshing at once; presenting an already-rotated
  token after that revokes the whole session.
- **Revocation.** Sessions live in Redis (`session:{sid}`) with a MongoDB record
  for audit and the admin UI. Logout, password change, role change and
  disabling an account bump the user's `tokenVersion`, so outstanding access
  tokens stop working on their next request (cached ≤ 60 s).
- **Fail closed.** If Redis is unavailable, authenticated requests get `503`
  rather than skipping session checks.
- **CSRF.** State-changing requests must send `X-Requested-With: XMLHttpRequest`
  (a header a cross-site form cannot set) and come from an allowed `Origin`.
- **Registration** always creates a `USER`. Any `role` field in the body is rejected.
- **Kokoon LMS sign-in** (`POST /auth/lms/sso`) takes a one-time HS256 token (≤120 s,
  `jti` remembered in Redis) instead of the CSRF header, and checks `Origin` against
  `LMS_URL`. It finds the user by LMS id, links an existing account only when the LMS
  verified the email, or creates a `USER` on the free plan. It never grants a role or plan.
  LMS-created accounts have no password until the student sets one under Profile.
- **Passwords**: Argon2id; 10+ characters with a letter and a digit.
  Login responses do not reveal whether an email exists.

## 6. Roles and permissions

`SUPER_ADMIN > ADMIN > DEVELOPER > USER`. Routes check explicit permissions
(`src/constants/permissions.constants.ts`), not role names alone, and services
additionally check ownership — knowing an id never grants access.

| Capability | USER | DEVELOPER | ADMIN | SUPER_ADMIN |
|---|:-:|:-:|:-:|:-:|
| Own projects, dashboards, variables, simulated devices | ✓ | ✓ | ✓ | ✓ |
| Send commands to own devices' variables | ✓ | ✓ | ✓ | ✓ |
| Publish free-form test messages (own device topics only) | | ✓ | ✓ | ✓ |
| Admin area: users, sessions, all projects, real devices, simulation, audit log | | | ✓ | ✓ |
| Change roles up to ADMIN / manage other admins | | | (below own rank) | ✓ |

Admins cannot modify accounts at or above their own rank, cannot demote the
last SUPER_ADMIN, and every privileged action and denied attempt is written to
the audit log.

## 6a. Plans and tokens

Every account has a **token build budget**: building costs tokens, deleting
refunds them. `used` is always computed from the workspace (never a stored
counter), so it cannot drift. See `src/constants/plans.constants.ts` and
`src/services/shared/token-wallet.service.ts`.

| | Tokens |
|---|---|
| FREE plan (every account) | `FREE_PLAN_TOKENS`, default 1,000 ≈ one project with 8 elements |
| PLUS plan (bought online, ₹`PLUS_PACK_PRICE_INR`, default 999) | `PLUS_PLAN_TOKENS`, default 10,000 |
| PREMIUM plan (kit owners) | `PREMIUM_PLAN_TOKENS`, default 50,000 ≈ 50+ dashboards of 8 widgets |
| New project (incl. its first dashboard) | 200 |
| Each extra dashboard | 100 |
| Each widget | 100 |
| Variables, devices, live data | free |
| Sample projects and the widgets they ship with | free |

- Enforced server-side on create project / duplicate / import / new dashboard /
  widget saves (`402 INSUFFICIENT_TOKENS`). Only growth is charged: moving,
  editing or removing widgets always saves, so a lowered budget never blocks
  or deletes existing work. One user's spending is serialised in-process.
- **Premium** is set by an admin (`PATCH /admin/users/:id/plan`, also bonus
  tokens) or by redeeming a **kit code** (`KOKO-XXXX-XXXX-XXXX`, generated
  under `/admin/kit-codes`, stored as SHA-256 hashes, single use,
  rate-limited). Redeeming a Premium code on a Premium account adds another
  full allowance as bonus tokens. Every change is audited.

### Payments

`/payments/catalog`, `/payments/orders`, `/payments/verify`, `/payments` (history),
`/payments/cancel`, `/payments/mock/complete` (test checkout only) and the
gateway webhook `POST /payments/webhook/razorpay` (raw body, HMAC-verified,
mounted before the JSON parser and CSRF check).

- `PAYMENT_PROVIDER=mock` (development default): built-in **test checkout**, no
  money moves; refused when `NODE_ENV=production`.
- `PAYMENT_PROVIDER=razorpay`: set `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET`
  (start with `rzp_test_` keys) and `RAZORPAY_WEBHOOK_SECRET`; add a webhook in
  the Razorpay dashboard for `payment.captured`, `order.paid` and `payment.failed`.
- Tokens are added only after the server verifies the gateway signature or
  a signed webhook, exactly once per payment (atomic `created → paid`).
  Getting the same or a lower plan again adds its allowance as bonus tokens; upgrading
  from Plus to Premium keeps the paid 10,000 as bonus.

Test accounts: `seed:dev` also creates `TEST_FREE_EMAIL` (Free) and
`TEST_PREMIUM_EMAIL` (Premium). `npm run kit:codes -- --count 5` prints new kit codes.

## 7. MQTT pipeline

- One shared backend connection. `MQTT_MODE=simulated` uses an in-process
  loopback transport (no network); `MQTT_MODE=broker` connects to the broker in
  `MQTT_BROKER_URL` with its own credentials (never sent to browsers).
- **Proposed topic convention** (the LMS MQTT block remains the authority):
  `{root}/{hardwareId}/telemetry/{key}`, `…/command/{key}`, `…/ack/{key}`,
  `…/availability`. Each device gets a server-assigned `topicPrefix`; variable
  topics outside it are rejected.
- **Ingest:** messages are matched to a known device, validated (size, JSON),
  batched into MongoDB with a TTL (`MESSAGE_RETENTION_HOURS`), latest values kept
  in Redis, and pushed over SSE only to users who own that device.
- **Commands:** `POST /mqtt/commands` checks ownership, coerces the value to the
  variable's type and range, publishes, and reports `pending` until the device
  acknowledges on its ack topic (5 s timeout → `failed`; an ack of
  `{"ok":false,"error":"…"}` → `failed` with the device's reason). Publishing is never
  shown as success on its own. Commands are rate-limited per user.
- **Demo simulation** (`DEMO_SIMULATION=true`) drives devices marked
  `simulated`, through the same pipeline. Every such message carries
  `simulated: true` and the UI labels it `SIM`. Real devices never receive fake data.

## 8. Logging

Winston with a request id and user id on every line (AsyncLocalStorage).
`LOG_DB_OPERATIONS=true` logs each DAO call (collection, operation, duration,
outcome) at `debug`. Passwords, tokens, cookies, `Authorization` headers,
broker credentials and secrets are redacted before anything is written, and MQTT
payloads are truncated. Files rotate daily under `logs/` when `LOG_TO_FILE=true`.

## 9. Environment variables

All variables are documented in `.env.example` and validated at startup —
the server refuses to start and names the offending variable when one is wrong.
In `NODE_ENV=production` it additionally requires: `COOKIE_SECURE=true`, an
`https` `FRONTEND_URL`, JWT secrets of 48+ characters that differ from each
other and from the example placeholders, a high-entropy `ENCRYPTION_KEY`, a TLS
broker URL (`mqtts://`/`wss://`) in broker mode, and `DEMO_WORKSPACE_ON_SIGNUP=false`.
With `LMS_INTEGRATION_ENABLED=true` it requires `LMS_URL`, both LMS secrets (48+ characters,
different from each other and from the JWT secrets) and `MQTT_PUBLIC_BROKER_URL`; in
production also an `https` `LMS_URL`, a TLS public broker and `BROKER_CREDENTIALS_MODE=mosquitto-dynsec`.

`.env` is git-ignored and must never be copied into the frontend.

## 11. Production checklist

- Run behind HTTPS (`COOKIE_SECURE=true`, `TRUST_PROXY` = number of proxies).
- Managed MongoDB replica set and Redis with auth + TLS; backups.
- A real broker (EMQX / HiveMQ / Mosquitto) with TLS, per-device credentials and topic ACLs.
- LMS integration: `BROKER_CREDENTIALS_MODE=mosquitto-dynsec`, LMS secrets only in the two
  backends' secret stores, and a public broker address with TLS.
- Secrets from a secret manager, not a file; rotate the JWT secrets to log everyone out.
- `DEMO_SIMULATION=false` unless you deliberately want demo devices.
- Ship logs to a central store; alert on auth failures and `auth.refresh.reuse` audit events.
- Commit a `package-lock.json` (see *Known limitations*) and run `npm audit`.

## 12. Known limitations

- **No `package-lock.json`.** This project was written in an environment
  without npm registry access. Run `npm install` once and commit the lock file.
- **LMS integration** (v1 contract, docs/LMS-INTEGRATION.md): the `mosquitto-dynsec`
  credential provider and its Docker profile have not been run against a real broker yet;
  `shared` mode gives every board the same broker account (development only). The LMS
  device upsert does not use a MongoDB transaction (see the doc).
- Devices registered by an admin in IoT Studio still use the shared device account;
  only LMS devices get per-device credentials (in `mosquitto-dynsec` mode).
- SSE fan-out is in-process: running several API instances needs a shared
  pub/sub (e.g. Redis) between them.
